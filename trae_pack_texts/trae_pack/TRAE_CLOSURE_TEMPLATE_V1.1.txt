TRAE_CLOSURE_TEMPLATE_V1.1 — MODÈLE CANONIQUE DE CLÔTURE

NOTE (opt-trading) : ce template doit refléter la structure canonique de continuité produit/plan validé.
Champs obligatoires pour la continuité : objectif final visé, état obtenu, établi, gap, prochain GO, reprise, séparation rôles (machine/IA-IDE/repo-produit).

NOTE (opt-trading) : ce fichier est un helper (support de format). La clôture canonique côté repo est `OT_*_CLOSING.txt` avec alignement doc canonique + kanban + point de reprise ; en cas de conflit, le repo prime.

## 1. OBJECTIF DU TEMPLATE
Standardiser l’archivage d’un état validé (mission, module, doctrine) afin de garantir que ce qui est clos est clairement identifié, que les décisions sont tracées et que le point de reprise pour la suite est explicite. Ce document marque la fin administrative d'une séquence validée.

## 2. CAS D’USAGE COUVERTS
- Fin de mission après verdict ACCEPT ou ACCEPT_WITH_NOTES.
- Stabilisation d'un module durable.
- Validation d'un document doctrinal.
- Fin de session de travail lorsqu’un état validé doit être archivé.

## 3. CHAMPS OBLIGATOIRES
- **Objectif final visé** : Rappel de l'objectif initial de la mission.
- **État obtenu** : Ce qui a été concrètement достиint.
- **Établi** : Ce qui est maintenant figé comme acquis.
- **Gap** : Ce qui reste à traiter ou n'a pas pu être fait.
- **Prochain GO** : Quelle est la prochaine étape GO ?
- **Reprise** : Point explicite pour relancer l'action future sans ambiguïté.
- Élément Cible : Nom précis de ce qui est clos.
- Statut Final : CLOSE.
- Référence Verdict : Rappel du verdict de review (ACCEPT / ACCEPT_WITH_NOTES).

## 4. CHAMPS OPTIONNELS
- Traçabilité Notes : Liste des TODO créés (si ACCEPT_WITH_NOTES).
- Artefacts Livrés : Liste des fichiers clés produits.
- Contexte Archivage : Date, version, ou lien vers le ticket.

## 1. OBJECTIF FINAL VISÉ
- [Rappel de l'objectif initial de la mission]

## 2. ÉTAT OBTENU
- [Ce qui a été concrètement atteint]

## 3. ÉTABLI
- [Ce qui est maintenant figé comme acquis]

## 4. GAP
- [Ce qui reste à traiter ou n'a pas pu être fait]

## 5. PROCHAIN GO
> **GO_<PROCHAINE_ÉTAPE_LOGIQUE>**

## 6. REPRISE
- [Point explicite pour relancer l'action future sans ambiguïté]

## 7. ÉTAT ÉTABLI (Légacy)
- **Cible** : <Nom du module / document / mission>
- **Statut Final** : CLOSE
- **Verdict de Référence** : [ACCEPT | ACCEPT_WITH_NOTES]

## 8. TRAÇABILITÉ (Si applicable)
- **Notes / Dettes** :
  - [x] <Référence ticket ou TODO créé>
- **Artefacts Clés** :
  - <Fichier 1>
  - <Doc A>

## 7. POINT DE REPRISE (Légacy)
> **GO_<PROCHAINE_ÉTAPE_LOGIQUE>**

## 6. RÈGLES DE REMPLISSAGE
1. Ne pas rejouer le match : Ce n'est pas le lieu pour discuter technique. C'est un constat administratif.
2. Être binaire sur le statut : ce template sert à archiver un état validé en CLOSE. Un élément en REJECT reste hors clôture tant qu’une autre décision doctrinale n’a pas été formalisée.
3. Lier le Point de Reprise : Le point de reprise doit être une commande ou un identifiant clair pour relancer l'action future sans ambiguïté.

## 7. ERREURS FRÉQUENTES À ÉVITER
- Clôture Floue : "On verra plus tard" (Pas de statut CLOSE clair).
- Oubli des Notes : Clore un ACCEPT_WITH_NOTES sans lister les tickets créés.
- Point de Reprise Manquant : Laisser le projet dans une impasse sans indiquer la suite.
- Confusion Verdict/Statut : Mettre "ACCEPT" dans Statut Final au lieu de "CLOSE".

(Motif de rejet : Pas de statut canonique, pas de référence verdict, point de reprise vague).

## 10. RÉSUMÉ TECHNIQUE COURT
Le TRAE_CLOSURE_TEMPLATE_V1.1 est le sceau final. Il transforme un travail technique validé en un acquis organisationnel pérenne. Il sécurise la mémoire du projet en figeant les succès (CLOSE) et en traçant les dettes acceptées, tout en fléchant immédiatement la suite des opérations via le Point de Reprise.

RÉSUMÉ DES CHANGEMENTS (V1 -> V1.1)

- Alignement CLOSE : Restriction du template aux seuls éléments validés (ACCEPT / ACCEPT_WITH_NOTES) passant en statut CLOSE. Exclusion explicite des REJECT.
- Nettoyage Cas d'Usage : Suppression des cas d'abandon/rejet pour se concentrer sur l'archivage positif.
- Format Canonique : Suppression de l'option REJECT dans le format.
